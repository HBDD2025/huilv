# 用卡速查维护规则

本项目用于用户日常用卡，页面为简体中文、朴实表格。已有请求授权：收到本专题中信用卡活动的新信息后，核验、压缩成可操作的结论，更新本仓库并发布。不要要求用户反复确认例行更新。涉及卡片归属不明、账户通知日期缺失时保留“账户待确认”，不猜测。

- 事实源：`data/cards.json`；页面模板：`web/template.html`。不要直接改生成文件后遗漏数据源。
- 每次先同步远程并阅读此文件、README 和最新数据；截图清单优先于旧聊天回忆。
- 每项活动记录适用卡、简要结论、门槛、上限、适用地区/渠道、登记要求、开始/截止日期、官方来源。
- 官方公开条款与用户定向活动分开；无法核验的用户截图标为待确认，不当成普遍权益。
- 新户申请广告不是用户当前持卡优惠，不自动收录。用户个人开卡任务只有已提供个人条件时才能记录。
- 账户信息（卡号、额度、开户日期、地址、账单、登录资料）不进入公开文件。个人任务可留在本地备注，用户明确允许公开后方可写公共数据。
- 老卡与新卡、公告与实际生效、自然年与持卡年都要分开。X 是对应积分单位，不能写成现金百分比。
- 检索同一卡所有官方相关页，避免只读搜索摘要。第三方 DP 单列待验证，不写成“保证报销”。
- `sources[].reviewedAt` 仅在实质阅读确认后更新。自动 HTTP 抓取不能更新该日期。
- 每次新增或修订条款补充 `changes`，写明新行为；过期活动保留记录，由页面自动归档。
- `source-status.json` 的 `needsReview` 只有阅读核验对应内容后才能清除；失败不能覆盖旧版正确权益。
- 运行 `python3 scripts/validate.py` 和 `python3 scripts/build.py`。提交并推送数据与生成页面；GitHub Pages 由 Actions 发布。不要只生成草稿就声称已上线。
- 不使用 `seed.py` 重建：首版数据已落地，后续直接编辑 JSON。
- 定时语义巡检的具体提示见 `MAINTENANCE.md`。定时任务必须获得 GitHub 可用读取与写入能力；未接通前不要声称自动维护已启用。

## 2026-10-23 用户新增要求及发布位置

- 首页优先消费用途查询，避免进入页面先展示大量权益。输入餐饮、电费、水费等列相关卡和好处。
- 每张卡显示保留积分单位的倍率，以及按可调整规划点值算出的回报区间；现金回馈独立标识。不得将主观估值冒充银行保证或“实际现金”。
- 官方倍率与估值假设分开；生活缴费不猜加倍；钱包渠道不保证传递分类；手续费可扣减。
- 手机使用纵向卡片。保留全部卡片、活动、清单与官方来源作为二级入口。
- 公开发布为 `HBDD2025/huilv` 仓库的 `cards/` 子目录，根目录 PayGlobe 不改。用户已明确“每次更新都上传一遍”，无需重复询问例行发布。
- 每次运行 `python3 scripts/validate.py`、`node scripts/test_recommend.cjs`、`python3 scripts/build.py`，将源文件和生成页一起提交，并核对 Pages 发布。

## 2026-10-23 商户查询补充

- 页面名称 Cards Magic by CZH；消费查询直接显示 11 张卡。
- 第三方旅行平台可模糊识别，但默认按普通合资格消费估算。账单确认银行的旅行/旅行社类别后，才展示适用的旅行类别加成；不得自动套用航空直购、酒店品牌直订或银行自家旅行门户奖励。
- 查询新商户时重置“已确认类别”的勾选。
